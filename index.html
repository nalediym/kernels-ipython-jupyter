kernels, ipython, jupyter

A hands-on playground for three words that get conflated constantly. The one idea underneath all of them: you touch a shell, a kernel does the real work.

The three layers

Kernel
The process that runs your code and holds its state.
IPython
The enhanced REPL that the default kernel wraps.
Jupyter
The front-end that talks to a kernel over ZeroMQ.

The pieces

  • The progression — flip through Unix → IPython → Jupyter: the same shell/kernel idea, rebuilt three times.
  • Build Your Own Jupyter — a notebook that's dead until you give it a kernel. Run it with no backend and it's just HTML; start the kernel (uv run python web/server.py) and every cell comes alive.
  • Code it from scratch — a day in the life of Thompson, Pérez, and the Jupyter team, assembled as the Builder pattern.
  • The raw ZeroMQ frames — boot a real kernel and read its sockets directly: the <IDS|MSG> delimiter, HMAC, header, content.
  • The executed notebook — the annotated playground, pre-run, with real outputs.
  • The writeup — the full essay on nalediym.github.io.

The lineage

Unix:     shell (bash)        ↔  kernel (Linux)        ← the OG pairing
IPython:  shell (the REPL UI) ↔  kernel (ipykernel)    ← borrowed the metaphor
Jupyter:  front-end (browser) ↔  kernel (any language) ← inherited it, 2014
